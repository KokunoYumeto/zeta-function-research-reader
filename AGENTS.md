# Canonical project pages

## Absolute rule

Zenodo's title and description, the GitHub repository description, and the main landing pages describe the whole project represented by their complete retained collection. They are canonical entry points for new readers, not announcements of the latest calculation.

Keep the project identity and title stable. Explain the purpose, principal objects, all substantive areas included, available papers and editable sources, human provenance and actual result scope. Keep a separate, subordinate section for the latest edition's changes. Review this description against the whole collection before each publication.

Individual papers, supplements, commits, diffs and pull requests describe their own scope. They do not need to repeat the whole project.

Programme citations must link to the actual public proof, preferably a pinned source version with a precise theorem, equation or source-line location. Preserve authorship, human citations and the exact mathematical content. Distinguish public reconstructions from private originals.

Keep a pertinent readable PDF as the Zenodo preview. An edition with no pertinent PDF provides a direct online reading link instead; a ZIP is an offline download, not a preview. Do not manufacture a PDF solely for the preview slot.

## One canonical Zenodo family

The sole project DOI is `10.5281/zenodo.22678085`, the version family containing record `22911829`. Add research directions and editions within this family. Never create a second continuation DOI family to avoid the 100-file limit; use complete ZIP archives while keeping the pertinent reader PDF as preview and all LaTeX available. The duplicate family is superseded by the consolidated edition. Preserve additive reader-facing contributions from other writers, including Claude. Re-read current GitHub and Zenodo state before publishing; never force-update Git or replace another writer's draft changes.
