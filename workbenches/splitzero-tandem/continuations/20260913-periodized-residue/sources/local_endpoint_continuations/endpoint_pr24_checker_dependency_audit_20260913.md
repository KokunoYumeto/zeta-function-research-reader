## Portable job plan and receipt interpretation

Use the current replay environment recorded by the owner's receipt, Python 3.13.9 with SymPy 1.13.1, as the explicit reproduction target. The author's older `VALIDATION.json` records Python 3.13.5/SymPy 1.14.0; that is a different historical run. The JSON specifies four direct original-core jobs, four direct proposed-core jobs, and two direct interface jobs. Set `PYTHONDONTWRITEBYTECODE=1` and pass `-B` in all commands; add `-O` only for optimized jobs. For each core, run one positive and one deliberate-negative job in each mode. Compare the complete parsed positive JSON objects for equality. Do not compare runtime-bearing unittest stderr byte-for-byte across fresh runs. Negative stderr contains the temporary source path and line number, so compare its expected exception text and exit code instead.

The interface jobs require an isolated mutable copy of `check_interfaces.py` and its unchanged original checker under the exact relative layout. Capture the generated receipt separately for each mode: running both modes in one directory overwrites the first receipt. Compare the full JSON objects after removing only the generated `created_utc` field. Preserve the pinned head, scope and all exact values. The existing interface receipt has 18 records: 17 are emitted by the `check` helper with result `pass`, and one records the asserted nonzero phase. In addition, the program contains explicit `eq`/`require` calls which are not each listed as a separate record. Do not advertise 18 unittest methods. The old receipt does not identify an optimization mode; the two proposed mode jobs are fresh work, not historical evidence.

`check_interfaces.py --negative-control` would not be a negative control: it ignores command-line arguments. No such job is listed. The interface has no internal timeout; the proposed external limit is 45 seconds. This is a scheduling bound for the future run, not a measured performance claim.

There is a relevant failure-reporting limitation in `replay_public_core.py:37–49`: a nonzero positive exit code is stored with `record=null`, and a timeout is recorded then breaks the loop. Neither case raises at the end. The wrapper can therefore itself exit zero while `both_full_modes_passed` is false. A portable driver should run the checker directly and enforce its exit code and record, as listed here, or explicitly enforce all wrapper receipt flags. The original wrapper's negative predicate accepts any nonzero code containing the target message, whereas the proposed direct jobs require exit 1. `replay_proposal.py` raises on nonzero positive exit, timeout, unexpected positive result, negative exit other than 1, and unequal positive mode records.

The positive checker JSON does not include `sys.flags.optimize`, the executable path, dependency versions, or a command array. The historical mode labels are supported by the inspected wrappers' child-command construction, not by a mode field emitted inside the checker. A future portable receipt should record its actual command, source/dependency hashes, runtime versions, and process result without editing the supplied checkers or rewriting the historical receipt.
